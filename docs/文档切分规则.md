# 文档切分规则

本文档规定 RAG 知识库的文档切分方式。当前采用“语义条目切分”（版本 B），不使用固定 `chunk_size` 作为正常切分规则。

## 1. 目标

每个向量库分片都应该是一个可以独立回答用户问题的最小知识单元。

切分结果需要满足以下要求：

- 问题和对应答案保存在同一个分片中。
- 故障现象、检测方法和修复方法保存在同一个分片中。
- 一条维护建议或一条选购建议作为一个分片。
- 不把两个无关的知识条目合并到同一个分片。
- 保留原始文件、章节和条目编号，方便检索结果追溯和评测。

## 2. 为什么不使用固定长度切分

固定长度切分会按照字符长度切分文本，可能把一个完整知识条目拆开，例如将问题和答案分到不同的分片中。当前实现优先使用语义解析器，`RecursiveCharacterTextSplitter` 只用于未知类型文档和超长条目的兜底处理。

本项目的知识文件本身已经具有明确的条目结构，因此优先使用标题和编号识别语义边界：

```text
文档
  └── 章节
       └── 一个问题、故障或建议
```

长度限制只作为超长条目的保护机制，不参与普通条目的切分。

## 3. 各类文件的切分单位

### 3.1 问答类文件

适用文件：

- `data/扫地机器人100问2.txt`
- `data/扫拖一体机器人100问.txt`

切分单位是“一条问题和对应答案”。例如：

```text
### 基础使用类
1. **机器人找不到充电座怎么处理？**
- 清理充电座周围障碍物，保证充电座前方3米、左右1米无遮挡。
```

生成一个分片：

```text
主题：基础使用类
问题：机器人找不到充电座怎么处理？
答案：清理充电座周围障碍物，保证充电座前方3米、左右1米无遮挡。
```

从一个编号条目开始，到下一个编号条目或下一个章节标题之前的所有文本，都属于当前问题的内容。

### 3.2 故障排除类文件

适用文件：

- `data/故障排除.txt`

切分单位是“一条完整故障记录”，必须保留：

- 故障现象；
- 检测方法；
- 修复方法。

例如：

```text
10. 机器人找不到充电座；
检测：充电座周围是否有遮挡，回充传感器是否有灰尘；
修复：清理充电座周围3米内障碍物，擦拭回充传感器。
```

应整体作为一个分片，不能按“故障现象”“检测”“修复”分别切分。

### 3.3 维护保养类文件

适用文件：

- `data/维护保养.txt`

切分单位是“一条完整维护建议”。章节标题需要附加到条目中，避免分片脱离上下文。

例如：

```text
主题：通用基础维护
建议：每日使用后，用干软布擦拭机器人机身外壳，去除灰尘和水渍。
```

### 3.4 选购指南类文件

适用文件：

- `data/选购指南.txt`

切分单位是“一条完整选购建议”。例如：

```text
主题：选购指南
建议：小户型优先选择轻便灵活、支持分区清扫的机型。
```

不同编号的选购建议不能合并到同一个分片中。

### 3.5 PDF 文件

适用文件：

- `data/扫地机器人100问.pdf`

PDF 页面不是语义边界。一个条目可能从一页开始，在下一页结束，因此不能直接把每一页当作一个分片。

处理流程是：

1. 提取每一页的文本。
2. 保留页码信息。
3. 合并跨页的连续文本。
4. 按章节标题和编号条目识别语义边界。
5. 将一条完整问题或建议生成一个分片。

页码保存到元数据中，作为来源定位信息，而不是作为切分规则。

## 4. 边界识别规则

### 4.1 章节标题

识别 Markdown 标题：

```text
# 标题
## 标题
### 标题
```

识别到章节标题时：

1. 保存当前正在构建的条目。
2. 更新当前章节名称。
3. 后续条目归入新的章节。

### 4.2 编号条目

识别以下形式的条目开头：

```text
1. 内容
2、内容
10. 内容
```

建议使用能够匹配数字加点号或顿号的规则：

```text
^\s*(\d+)[.、]\s*(.+?)\s*$
```

识别到新的编号条目时，先保存上一个条目，再开始构建新条目。

### 4.3 条目续行

既不是章节标题、也不是新编号的文本，全部追加到当前条目中。例如：

```text
检测：检查尘盒是否堵塞；
修复：清理尘盒并重新启动机器人。
```

这些内容属于前面的编号条目，不能单独生成分片。

### 4.4 文档开头的普通标题

有些文件的第一行不是 Markdown 标题，例如：

```text
扫地/扫拖一体机器人故障检测与修复200条
```

如果该行位于第一个编号条目之前，可以作为文档标题或默认章节名称保存到元数据中。

## 5. 分片输出格式

每个分片应该生成一个 LangChain `Document`。

### 5.1 `page_content`

用于 Embedding 的正文必须包含必要的主题上下文：

```text
主题：故障报警类
故障现象：机器人找不到充电座
检测：充电座周围是否有遮挡，回充传感器是否有灰尘
修复：清理充电座周围3米内障碍物，擦拭回充传感器
```

### 5.2 `metadata`

每个分片至少保存以下字段：

```python
{
    "source": "故障排除.txt",
    "section": "故障报警类",
    "entry_no": 10,
    "chunk_type": "fault",
    "chunk_id": "故障排除.txt_故障报警类_10",
}
```

PDF 分片还应保存页码：

```python
{
    "page_start": 2,
    "page_end": 3,
}
```

`entry_no` 不能单独作为唯一标识，因为不同章节可能重复使用相同的编号。`chunk_id` 至少应由文件名、章节和条目编号共同组成。

## 6. 分片类型

建议通过 `chunk_type` 标记分片类型：

| 类型 | 含义 |
| --- | --- |
| `qa` | 问题和答案 |
| `fault` | 故障现象、检测和修复 |
| `maintenance` | 维护保养建议 |
| `selection` | 选购建议 |

该字段可以用于后续评测、过滤和统计。

## 7. 超长条目处理

正常情况下不按照固定 `chunk_size` 切分。如果单个语义条目异常长，才进行二次处理：

1. 先保留完整条目作为逻辑父条目。
2. 按句号、问号、分号等自然边界拆分。
3. 子分片继承父条目的主题、来源和编号。
4. 子分片增加 `parent_chunk_id`。

例如：

```python
{
    "chunk_id": "故障排除.txt_故障报警类_10_1",
    "parent_chunk_id": "故障排除.txt_故障报警类_10",
}
```

超长保护不应破坏问题和答案、故障和修复之间的基本对应关系。

## 8. 切分结果检查

在写入 Chroma 之前，必须先检查切分结果：

- 每个分片是否只包含一个编号条目；
- 问题和答案是否位于同一个分片；
- 故障现象、检测和修复是否位于同一个分片；
- 是否存在空分片；
- 是否有条目被遗漏；
- `chunk_id` 是否重复；
- 章节名称是否正确；
- 文件来源和 PDF 页码是否保留；
- 是否有上一章节的内容错误地进入下一章节。

建议先打印每个文件的分片数量、前几个分片和后几个分片，人工确认后再建立向量库。

## 9. 向量库重建要求

切分规则改变后，原有向量库不能直接复用，因为原有分片内容已经发生变化。

切换到本规则后，需要删除旧的向量库和文件处理记录，再重新导入：

```bash
rm -rf chroma_db
rm -f md5.text
python3 -m rag.vector_store
```

后续如果同时保留多个切分策略，应为不同策略使用独立的 Chroma 持久化目录和 MD5 文件，例如：

```text
chroma_db/semantic_item/
md5.semantic_item.text
```

## 10. 当前实验建议

第一阶段只改变切分策略，保持以下参数不变：

- Embedding 模型；
- `k` 值；
- 原始知识文件；
- 检索问题集合；
- RAG 提示词。

先比较当前固定长度切分和本语义条目切分的检索结果，再研究不同 Embedding、`k` 值、混合检索和 reranker。这样可以明确判断效果变化来自切分策略还是其他因素。
